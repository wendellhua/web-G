# 《黑潮突围（VOID RUNNER）》项目级工程规则（SDD-G CLAUDE.md）

> **适用项目**：《黑潮突围（VOID RUNNER）》—— 纯前端 PC 端（16:9 横屏）无限大地图生存割草肉鸽网页游戏  
> **治理定位**：本项目最高约束宪章。AI 在需求梳理、灰盒原型、系统设计、编码实现、测试验证全生命周期中，必须严格遵守以下规则；违反任一条核心红线均视为不合规，必须修正后方可进入下一阶段。

---

## 1. 阶段 1 规则：游戏概念与核心玩法规格梳理

适用范围：需求梳理、玩法探索、产出 `docs/01.游戏设计规格书(GDD-Lite).md` 阶段。

1. 有任何不确定的玩法规则、数值范围、系统边界或交互细节，必须与用户逐轮交互确认，等用户回答后再继续追问，**禁止一次性把所有问题全部抛出**。
2. 一轮一轮推进（每轮聚焦 2~4 个关键问题），直到核心循环与架构级关键决策全部清晰、无阻塞性问题为止。
3. 每轮结束时，必须输出一份简短的**「当前规格快照」**：包含 `已确认结论`、`待确认清单`、`本轮新增结论`。
4. 每个问题必须具体、可决策，禁止提出"你想要什么玩法"这类空泛问题；尽量给出候选选项与专家倾向建议。
5. 每个问题必须简要说明 **"为什么问"**，明确指出该问题影响哪些后续架构、状态机或工作量决策。
6. 优先提出最影响底层架构与开发落地的问题（例如：操作模式、视觉表现策略、同屏规模、单局节奏、局外成长范围）。
7. 本阶段**禁止编写任何代码**，禁止提前讨论具体引擎 API 实现细节，禁止替用户编造未确认的设定。

---

## 2. 阶段 2 规则：核心玩法灰盒原型验证

适用范围：产出 `prototype/` 可玩灰盒原型及 `docs/02.灰盒原型验证结论.md` 阶段。

1. 灰盒原型必须完全隔离在 `prototype/` 目录下独立运行，**严禁被后续 `src/` 生产代码 `import` 或直接演进为正式项目**。
2. 灰盒原型仅使用纯色几何图形（如圆/方/三角/线条）验证核心移动、瞄准射击、敌人追击与碰撞、经验拾取、基础刷怪节奏和手感，**禁止在本阶段制作复杂美术、主菜单、本地存档、永久天赋树和多关卡内容**。
3. 原型页面必须内置轻量**实时调参浮窗（Debug Tuning Panel）**，方便用户在试玩时实时调节移速、射速、碰撞半径、击退、怪群密度等基线手感参数。
4. 原型验证结束后，必须沉淀《02.灰盒原型验证结论.md》，明确记录已验证通过的机制、需调整/砍掉的机制以及锁定后的手感基线参数，经用户确认后方可进入阶段 3。

## 3. 阶段 3~7 规则：系统设计、契约定义与方案评审

适用范围：产出 `docs/03` ~ `docs/07` 设计文档与 `schemas/` 契约骨架阶段。

1. 总体设计阶段以分析、方案讨论、契约冻结与文档编写为主；**未经用户明确批准进入阶段 8，严禁编写或修改 `src/` 下的生产业务代码**。
2. 所有设计必须以已确认的 `docs/01.游戏设计规格书(GDD-Lite).md` 和 `docs/02.灰盒原型验证结论.md` 为依据，不得脱离项目实际凭空发挥。
3. 状态机、运行时架构、静态配置表、本地存档结构、内部通信契约与资源清单之间必须保持 **100% 命名与类型一致**。
4. 规格发生变更时，必须检查并同步更新所有受影响的设计文档，并在评审报告中留下变更记录。
5. 对核心玩法规则、状态迁移、配置 Schema、存档结构、核心技术栈的重大调整，必须先提出方案并获得用户确认。
6. 遇到需求歧义、设计冲突或信息缺失时，必须明确指出并询问，**严禁将未经确认的推断当作既定事实**。
7. **禁止擅自增加规格外功能**（如私自加入在线排行榜、复杂剧情对话、多语言系统、成就弹窗等）；如确有工程必要，先提议再决策。
8. 按阶段粒度逐一审核确认，不得为了图快跳过状态机、数据契约或跨文档一致性评审。

## 4. 运行时架构与无头解耦规范（最高技术红线）

本规范指导《黑潮突围》的核心引擎与运行时架构设计，确保高帧率稳定、跨刷新率一致、且 100% 可自动化仿真测试。

1. **严格无头核心（Headless Core）**：
   - `src/core/` 目录下所有文件**严禁引用** `window`、`document`、`HTMLCanvasElement`、`CanvasRenderingContext2D`、`AudioContext`、`localStorage`、`IndexedDB`、`requestAnimationFrame`、`performance.now()` 或 `Math.random()`。
   - 核心模拟层必须能够在纯 Node.js（无浏览器环境）下直接导入、创建世界、单步推进并完成整局模拟。
2. **固定时间步长循环（Fixed Timestep）**：
   - 核心世界推进必须统一通过 `world.step(FIXED_DT, commands)` 执行（推荐 `FIXED_DT = 1 / 60` 秒）。
   - 浏览器宿主层（`src/main.ts` / Adapter）必须对每帧原始帧间隔做上限钳制（`rawDt = Math.min(rawDt, 0.05)`）并限制单帧最大子步数（`MAX_SUBSTEPS = 5`），彻底杜绝高刷屏（120Hz/144Hz）倍速运行、低帧率螺旋死亡及切后台切回穿墙问题。
3. **确定性随机（Seeded PRNG）**：
   - 刷怪位置、三选一词条抽取、暴击判定、祭坛生成、宝箱掉落等一切核心随机逻辑，必须使用统一注入的 `SeededRNG` 实例；禁止在 `src/core/` 中调用原生 `Math.random()`。
4. **单向数据流与只读隔离**：
   - 依赖方向严格单向：`Input → Command → Core → (Readonly RenderSnapshot + GameEvents) → Render / Audio / UI`。
   - 表现层（`src/presentation/`）与界面层（`src/ui/`）**严禁直接修改** Core 内部实体属性；所有玩家操作必须封装为标准 `GameCommand` 或经由 `GameController` 派发。
5. **同屏海量实体性能红线（《黑潮突围》专项）**：
   - 针对无限大地图同屏 200~500+ 敌人/弹幕/经验宝石的碰撞压力，Core 碰撞检测必须采用**空间哈希网格（Spatial Hash Grid）**或等效空间索引，严禁使用全量 `O(N²)` 暴力双层循环。
   - 必须明确并强制执行单帧实体软/硬上限预算（敌人、投射物、经验宝石合并策略、粒子上限）。
6. **彻底重置契约（Clean Reset Contract）**：
   - 重开一局或返回标题页必须执行统一 Reset 流程，清空全部实体、波次计时器、对象池活跃引用、待消费指令队列与临时事件订阅，确保第 N 局与第 1 局初始状态完全等价、零内存泄漏。

## 5. 数据模型、静态配置表与本地持久化规范

本规范替代传统企业 SDD 的《数据库设计规范》，约束纯前端游戏三大数据域。

### 5.1 命名与单位规范
1. TypeScript 接口/类型/类使用 `UpperCamelCase`（如 `WeaponConfig`、`EnemyEntity`）；字段与变量使用 `lowerCamelCase`（如 `cooldownMs`、`moveSpeedPxPerSec`）；全局常量使用 `UPPER_SNAKE_CASE`（如 `FIXED_DT_SEC`、`MAX_ACTIVE_PARTICLES`）；ID 键值统一使用小写下划线 `snake_case`（如 `void_bolt`、`elite_stalker`）。
2. 所有物理与时间数值字段**必须在命名或 Schema 注释中显式标明单位**（如 `Ms`/`Sec`、`Px`/`WorldUnit`、`Rad`/`Deg`、`Ratio`），严禁出现单位不明的裸数值字段（如 `speed: 5`）。
3. 状态字段必须采用有限联合类型或常量枚举（Union Type / `const` enum-like object），严禁使用散落的魔法字符串。

### 5.2 静态配置表（数据驱动）规范
1. 角色属性、主动武器、被动核心、超武合成配方、敌人模板、波次导演时间线、地图祭坛事件、局外永久天赋树数值，**一律收敛至 `src/config/` 静态配置表**。
2. 禁止在 `src/core/systems/` 逻辑代码中硬编码业务数值（如伤害、冷却、血量、经验阈值、刷怪间隔）。
3. 所有配置表在启动/测试阶段必须通过 Schema 校验（如 Zod 或等价校验器），防止非法负数、除零参数、引用不存在的 `weaponId`/`evolutionId` 或权重全为 0。

### 5.3 运行时状态与对象池规范
1. 高频创建与销毁的实体（敌人、子弹、经验宝石、伤害飘字、粒子）必须定义明确的对象池结构与容量上限；热路径（60FPS `step()` / `render()`）严禁每帧无意义创建大量短生命周期数组/对象或深拷贝整个世界状态。
2. 关键计算（伤害公式、经验曲线、冷却缩减）必须具备数值护栏（如最小冷却下限、血量非负钳制、除零保护），确保绝不产生 `NaN` 或 `Infinity`。

### 5.4 本地持久化与存档迁移规范
1. 本地存档数据结构必须显式包含 `schemaVersion: number`、`updatedAt: number` 与清晰的域分区（如 `metaProgress`、`unlocks`、`runStats`、`settings`）。
2. 必须实现版本迁移管道（`migrateSave(raw): SaveDataVCurrent`）；数据结构升级时严禁直接破坏旧版玩家存档。
3. 存储访问必须封装在 `src/storage/` 中并全程 `try/catch`：当浏览器处于无痕模式、配额满或 JSON 损坏时，必须安全降级为内存态运行并记录告警，**绝不允许抛异常导致游戏白屏**。
4. **严禁在 60FPS 主循环内执行 `localStorage.setItem` / IndexedDB 写入**；落盘仅允许发生在结算、天赋购买、设置变更、手动保存等低频安全节点。

## 6. 内部通信契约、事件总线与资源/视听规范

本规范替代传统企业 SDD 的《API 接口设计规范》，约束模块间通信与浏览器视听资源。

### 6.1 内部模块契约
1. **输入契约（Input → Command）**：键盘方向输入（WASD/方向键，对角线速度归一化）与功能热键（`1/2/3` 选卡、`R` 重随、`Esc/P` 暂停、`Space/Enter` 确认）统一归一化为 `GameCommand`，支持键位冲突与页面失焦按键状态自动释放（纯自动武器释放流，无手动瞄准与主动冲刺）。
2. **快照与事件分离原则**：
   - 持续性状态（实体位置、朝向、血条、经验条、时间、击杀数）通过只读 `RenderSnapshot` / `HudSnapshot` 读取；
   - 瞬时反馈（受击、暴击、击杀、升级、拾取宝石、超武觉醒、祭坛激活、Boss 预警）通过强类型 `GameEventBus` 派发，事件在每帧消费完毕后清空，防止事件堆积。
3. **UI 控制器契约**：UI 层只能调用 `GameController` 暴露的幂等方法（`startRun`、`pause`、`resume`、`chooseUpgrade`、`restartRun`、`returnToTitle`、`buyTalent`、`setAudioVolume`），不得直接操作底层循环或世界对象。
4. **调试与自动化测试钩子契约**：开发/测试环境下允许通过受控接口（如 `window.__VOID_RUNNER_DEBUG__`）暴露只读状态查询、固定种子开局、单步推进与指定测试状态注入，生产构建默认关闭或受开关控制。

### 6.2 资源与视听反馈规范
1. **强类型资产清单（Asset Manifest）**：若使用外部图片、字体、音效文件，必须全部在 `src/assets/manifest.ts` 注册唯一 `AssetId`；业务与渲染代码禁止硬编码文件路径字符串。
2. **程序化绘制优先与缺失兜底**：本项目优先采用高质量程序化 Canvas 2D 矢量/几何荧光渲染与 Web Audio 程序化合成音效；若引入外部资源，加载失败时必须无缝降级为程序化占位图，绝不阻断游戏启动。
3. **Web Audio 宿主合规与防破音**：
   - 必须在首次用户手势（点击/按键）后安全 resume/解锁 `AudioContext`；
   - 高频音效（射击、命中、经验拾取）必须实施**最小触发间隔节流（Throttle）与最大并发轨道上限**，严禁百怪同死时音频爆音炸麦；
   - 必须提供独立主音量、BGM 与 SFX 音量控制及一键静音，并持久化至本地设置。
4. **Game Feel 职责隔离**：顿帧（Hitstop）、屏幕震动、受击闪白、伤害飘字、粒子爆发、吸星拖尾均属于 `src/presentation/` 表现层（或受控视觉特效状态），不得破坏 Core 逻辑确定性。

## 7. TypeScript 纯前端工程开发与质量门禁规范

### 7.1 技术栈约束（经阶段 4 最终确认后锁定）
- 语言与构建：TypeScript（`strict: true`）+ Vite
- 渲染与 UI：Canvas 2D（或阶段 4 确认的渲染方案）+ 轻量化 DOM/CSS HUD 叠层
- 校验与测试：Vitest（单元测试 + 无头万帧仿真）+ Playwright（浏览器 E2E 与零报错门禁）+ ESLint

### 7.2 编码纪律
1. 开启 `strict: true`、`noUncheckedIndexedAccess: true`、`noUnusedLocals: true`；禁止使用 `any`（必要外部边界使用 `unknown` + 类型守卫收窄）。
2. 禁止静默吞掉异常的空 `catch {}`；所有容错分支必须说明原因并执行明确的降级动作。
3. 模块单向依赖必须严格遵守 `src/main.ts → ui / presentation / input → core → config`；禁止循环依赖（Circular Dependency）。
4. 浏览器宿主生命周期守卫：必须监听 `visibilitychange` 与 `window.blur`，页面失焦/切后台时自动进入 `PAUSED` 状态并暂停音频；必须正确响应窗口 `resize` 与 `window.devicePixelRatio`，保持 16:9 清晰无模糊渲染。
5. 注释简洁准确：重点解释物理公式意图、空间网格参数、状态机边界条件和关键架构取舍，禁止复述代码字面含义的废话注释。

### 7.3 分层交付与提交门禁（Stage 8 & Stage 9 强制执行）
1. 阶段 8 必须按 **L1 骨架与配置/存档 → L2 无头核心引擎 → L3 渲染与视听 → L4 UI 闭环 → L5 内容与平衡填充** 五层顺序递进，严禁跨层混写。
2. **每层完成门禁**：
   - `npm run typecheck`（零 TS 错误）
   - `npm run lint`（零 Lint 错误）
   - `npm run test:unit`（当前层及之前所有单元测试 100% 通过）
3. **最终发布门禁（阶段 9）**：
   - 无头确定性万帧仿真压测（`npm run test:sim`）：多组随机种子下 100% 无 `NaN`、无死循环、无实体数失控爆炸；
   - Playwright E2E 回归（`npm run test:e2e`）：覆盖开局 → 操作 → 升级三选一 → 暂停/恢复 → 结算 → 重开 → 刷新读档全链路，断言 **Zero Console Error、Zero Page Error、Zero 404、Canvas 非纯黑/空白**；
   - 人类试玩终验：确认 60FPS 稳定、切后台无穿墙、音画与打击感达标。
